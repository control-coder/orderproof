# 评测与验证

以下都是小规模工程验证，数据为模拟订单，只覆盖六类受限分析。每个对照只运行一批，1–2 例的差异不代表稳定差距；时延受并发和供应商负载影响，不代表生产 SLA。逐例原始结果写入被忽略的 `artifacts/evals/`，没有随仓库发布。

## 判定口径

- 正确：任务成功，并且结果等于按题意人工写定的真值计划的独立参考结果。只通过核验不算正确，因为核验只能证明代码忠实于模型自己的计划。
- 首次即对：不经过任何代码修正或核验反馈就正确。
- 费用：按接口返回的用量和以下单价计算，单位为元/百万 token：输入未命中缓存 1，命中缓存 0.02；输出 MiMo 2，DeepSeek 4。

## 当前结果

### 单 Agent 与三角色、有 Memory 与无 Memory

命令：`python -B evals/model_compare.py --providers mimo,deepseek --workers 4`。

- 数据：固定种子 20260928 生成的 2000 行模拟订单，时间为 2026-07 至 09，四个渠道、四个品类，paid/refunded/cancelled 约为 80/12/8。
- 模型：`mimo-v2.6-flash`、`deepseek-flash`，温度 0.2，JSON 模式。
- 固定因素：同一数据、题目、受限容器、独立 SQL 核验、修正次数（一次代码修正和一次核验反馈），以及任务预算（6 次调用、15 万 token、600 秒，单次输出上限 16384）。
- 单 Agent：一次调用同时给出计划和 `analyze` 函数，执行、核验和修正规则与三角色相同，没有 Reviewer。
- Memory 对照：4 个项目各自可信预配置一条“成交额”口径并写入 PostgreSQL，每个项目 2 个会话，问题中不复述口径。有 Memory 时，每个会话都新建服务实例，从数据库取回已确认口径。无 Memory 时，产品的实际行为是进入等待确认、不调用模型；为了量化风险，评测脚本额外让模型自行判断纳入状态。这条绕过只存在于评测脚本中，产品路径不允许。

- 三角色和单 Agent 在两个模型上的正确率持平，没有超过单 Agent。三角色的平均费用约为单 Agent 的 1.4 倍（MiMo）和 2.4 倍（DeepSeek），中位时延约为 2.4 倍。DeepSeek 倍数更高，是因为推理 token 多、输出单价也高。
- DeepSeek 有 4 例首次未通过独立核验（三角色 1 例、有 Memory 2 例），都在一次定位反馈后改对。这批运行中，Reviewer 没有驳回已通过核验的结果，也没有跳过审查。

### 真实模型全链路冒烟

命令：`python -B evals/model_app_smoke.py`。流程为：经 API 建项目、上传上述 2000 行订单并确认“仅统计已支付订单”口径，任务经 Redis 派发给 2 个 Celery worker，依次走完三角色、受限容器、独立核验与图表说明派生。六类分析各一题。

判定：核验参考结果与真值计划的独立计算一致；说明中含口径版本；除 summary 外都有图表，每张 PNG 都能经 `?inline=true` 以 `image/png` 返回。

| 模型 | 正确 | 图表与说明 | 模型调用 | token | 执行尝试 |
| --- | --- | --- | --- | --- | --- |
| MiMo | 6/6 | 6/6 | 18 | 28,965 | 6（均一次通过） |
| DeepSeek | 6/6 | 6/6 | 18 | 48,191 | 6（均一次通过） |

图表共 12 张：趋势、排行、期间对比各 2 张，占比 3 张，数据质量 1 张，summary 无图。人工查看了 MiMo 的趋势图，最高点与末点标注正确。DeepSeek 的趋势题单例用了 17,678 token，其余题约 4–9 千。耗时包含排队，只说明链路能在预算内完成，不作为时延指标。

### 固定种子评测（不调用模型）

命令：`python -B evals/run_suite.py`。种子 20260926；三个角色都使用确定性固定后端，执行走真实 Docker 与 PostgreSQL。

| 类别 | 结果 | 方法与边界 |
| --- | --- | --- |
| 数值 | 20/20 | 对模拟订单构造六种分析与日期、分组选项，另用按行过滤、整数汇总的纯 Python 公式独立对照参考值，不以核验器自报成功代替外部基准 |
| 业务记忆 | 8/8 | 真实 PostgreSQL：待确认、跨会话、跨项目/家族/结构隔离、冲突、快照版本与失效 |
| 故障 | 8/8 | 6 项真实 Docker 场景（权限/网络/文件隔离、超时、取消、符号链接、磁盘、内存）；1 项模拟“Reviewer 不能自我批准”；1 项真实数据库最终取消竞争 |

数值任务的服务内执行中位延迟为 1.730 秒，最近秩法 p95 为 1.898 秒（20 例，测试机单次结果），不含浏览器、队列、网络与人工确认。模型 token 为 0，因为使用的是固定后端。

### 规模

命令：`python -B scripts/verify_scale.py`。十万行模拟 CSV（18,400,054 字节，上限 20,971,520 字节）导入 1.732 秒；完整固定汇总加真实容器与独立核验合计 4.905 秒，其中容器执行 2.235 秒；结果为 100,000 笔、15,000,000 分，核验成功。只测了汇总这一种分析和一台机器上的一个样本，不代表端到端队列 p95 或其他十万行组合的速度。

## 迭代过程

### 首次对照（2026-09-28）

第一次正式运行时，DeepSeek 三角色 0/20，MiMo 三角色 14/20（费用 0.60 元）。原因是两款 flash 模型的推理 token 计入 `max_tokens`：上限为 4096 时，DeepSeek 的 Analyst 在思考阶段就耗尽额度，正文为空；适配器又把“截断且正文为空”报告成“未返回内容”。修正方式：单次输出上限改为 16384，请求超时 180 秒，任务预算改为 15 万 token / 600 秒；适配器先检查 `finish_reason=length`，截断时报告为截断。

修正后的第二次运行，共 112 例，费用 2.70 元：

| --- | --- | --- | --- | --- | --- | --- |
| 单 Agent | MiMo | 20/20 | 17 | 18.6 / 28.7 | 4473 | 0.0066 |
| 三角色 | MiMo | 18/20 | 13 | 86.5 / 219.9 | 9804 | 0.0147 |
| 单 Agent | DeepSeek | 20/20 | 18 | 10.9 / 21.2 | 5624 | 0.0158 |
| 三角色 | DeepSeek | 16/20 | 15 | 42.7 / 62.7 | 14172 | 0.0465 |
| 有 Memory | MiMo | 7/8 | 4 | 82.6 / 300.6 | 9726 | 0.0143 |

- 80 道数值题的计划全部正确，失败都发生在代码生成、输出契约或 Reviewer 环节。
- 三角色的 token 为单 Agent 的 2.2–2.5 倍，费用 2.2–2.9 倍，中位时延 3.9–4.6 倍。
- MiMo 的 Reviewer 在 5 个任务中驳回了 6 次已通过独立核验的结果，第 11 题仅因驳回而失败。DeepSeek 三角色有 3 例失败是 Analyst 输出契约问题或截断（2 例非 JSON、1 例超长）。
- 无 Memory 时出现 9 个“独立核验通过、Reviewer 也接受，但数值不符合项目口径”的结果（MiMo 4、DeepSeek 5）。
- MiMo 最长单例为 504–567 秒，接近 600 秒预算。

正式运行前，有一次 8 个任务的试跑（约 0.05 元）。试跑发现，问题未限定期间时 Planner 会用 `time_min/time_max` 填充期间，导致计划无效；之后在 Planner 提示中写明“未限定时为 null”。试跑题目与正式题目有重叠，存在少量按评测集调提示的偏差。

### Reviewer 交接与驳回路由

逐例记录与代码核对后，找到以下根因：

| 根因 | 依据 | 修正 |
| --- | --- | --- |
| Reviewer 对已通过核验的结果有一票否决权，驳回意见却被送给只能改代码的 Analyst | 原成功条件为 `check.passed and review["accepted"]`；MiMo 有 4 例同一计划、同一核验先被驳回、后被接受；DeepSeek 第 18 题首次已通过核验，驳回后 Analyst 重写反而未通过 | 驳回改为交回 Planner 复核一次 |
| 要求 Reviewer 判断计划是否符合问题，交接里却没有问题 | 重放中，读错题的计划有 13/16 被接受 | 交接加入问题与数据概况，提示只审类型、分组与期间 |
| 计划声明了不存在的 `refund_filter` 检查 | 默认值包含它，但没有任何代码实现，Reviewer 几乎每次都追问 | 默认值改为实际执行的检查；交接中的计划不带 `checks` |
| 参考数值可能经审查意见回流给 Analyst | Reviewer 收到完整参考结果，其反馈原样回传 | Reviewer 只收到检查名与结论；核验失败时不再调用 Reviewer |
| 调用越多，契约失败机会越多 | DeepSeek 有 2 例 Analyst 非 JSON，原始响应未记录，确切原因无法确认 | 核验失败时少一次调用；解析时允许字符串内的原始换行和制表符（`strict=False`） |

还验证过一个假设：`checks` 字段导致 Analyst 额外推理。去掉该字段后，MiMo Analyst 的平均输出 token 从 2691 降到 2601，基本不变，假设不成立。

Reviewer 单角色重放（`evals/review_replay.py`，只用 MiMo）：20 个正确计划和 8 个人工构造的读错题计划，各重复 2 次，核验都标为通过。

| 版本 | 正确计划被接受 | 错误计划被拒绝 | 平均输出 token |
| --- | --- | --- | --- |
| 修正前 | 38/40 | 3/16 | 315 |
| 修正后（第一版提示） | 38/40 | 16/16 | 310 |
| 修正后（补充 quality 与分组说明） | 40/40 | 16/16 | 162 |

第一版提示下被误拒的两次都是第 20 题，模型认为 quality 应按 status 分组。补充说明来自同一题集，存在按评测集调提示的偏差。

### 定位反馈、代码框架与审查降级

针对上面第 18 题（Analyst 只知道检查名，修正时改坏了原本正确的部分）和 Analyst 输出偏长的问题，做了三项修改：核验反馈只定位错误、不给期望值；计划常量、读写与防护由服务端框架生成，模型只写 `analyze`；Reviewer 使用独立限额，失败时跳过审查。单 Agent 对照组使用同样的反馈和框架，两组仍然只差角色拆分。

Analyst 单角色重放（`evals/analyst_replay.py`，只用 MiMo）：对 20 道题的真值计划各调用 2 次，不带反馈，在真实容器中执行并独立核验。

| 变体 | 首次核验通过 | 平均输出 token | 平均输入 token | 模型中位 / p90 秒 | 费用（元，40 次） |
| --- | --- | --- | --- | --- | --- |
| full：完整脚本提示 | 34/40（执行失败 2） | 2981 | 1126 | 29.6 / 61.5 | 0.284 |
| func：框架，只写 analyze | 37/40 | 1344 | 887 | 16.7 / 31.6 | 0.117 |
| helpers：func 加辅助函数说明 | 35/40（连接失败 2、执行失败 1） | 1195 | 1000 | 12.0 / 31.0 | 0.103 |

最终合入的是 func：helpers 的通过率没有更高，还多一段需要维护的提示。full 的失败大多是下载表列不符和执行失败，正是框架接管的部分。三个变体都有“comparison 缺失”的失败，这属于计算逻辑问题，框架覆盖不了。

| --- | --- | --- | --- | --- | --- |

- 两组都便宜了约 40%。这是整体降本，并没有缩小三角色与单 Agent 的相对差距。
- 有 2 例首次未通过的任务，各靠一次定位反馈改对：一例是 `rows[i].share` unexpected（趋势题多输出了占比列），另一例是 `comparison` missing。
- 三角色的额外开销主要来自 Planner 和 Reviewer 两次独立调用，以及 Analyst 与单 Agent 首次调用之间的差异（平均输出 1386 对 945 token），后者的原因还没有查明。

## 工程验证中的失败与修复

- 初次 8 项记忆评测只有 4 项通过。原因是评测本身把已确认的数值口径和待确认记忆放在同一范围，破坏了“没有默认规则”的前置条件。拆分评测的语义范围后，完整重跑为 8/8。
- 浏览器实测时发现两个问题：项目切换与上传并发时，新数据被旧列表覆盖；跨页面跳转时，报告路由丢失任务 ID。分别修复了数据版本合并和报告 hash，并重跑了 Edge 流程。
- worker 提交成功与取消请求存在竞争。新增了真实数据库行锁回归测试：取消先于终态提交确认时，不再发布成功。
- 默认 API 端口 8000 在测试机上不能绑定，改为回环 18080，并同步更新 Origin 校验。

## 局限与未验证范围

- 题集只有 20 道数值题和 8 个记忆会话，数据是合成的，只覆盖六类受限分析；部分提示调整来自同一题集。
- 在当前任务集上，三角色没有在正确率上超过单 Agent。这不能证明多角色在需要跨步骤澄清的复杂问题上也没有收益。
- Reviewer 能拒绝重放中全部 16 个读错题的计划，但在全量对照里 Planner 的计划本来就全对，这项能力没有转化为正确率差异。
- “驳回后交回 Planner 复核”和“审查降级”两条路径在真实模型运行中没有被触发，只有离线测试覆盖。
- 结果只针对 `mimo-v2.6-flash` 和 `deepseek-flash`，没有重复多批来取区间。
- 图表字节级可复现性依赖字体，Linux 字体下的输出没有比较过。
- 只在一台 Windows 主机上验证过；生产部署、公网认证、多用户与跨平台运行都不在已验证范围内。
